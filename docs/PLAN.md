# Single Chat 开发计划

> 一个只做 Android 的纯聊天应用。原则：**把通道能力交给成熟 PaaS，把产品体验留给自己**。

## 1. 项目目标

- 做一款打开就能聊天、没有信息流的轻量聊天 App。
- 单端 Android，不背跨端包袱。
- 第一阶段用云 IM 快速跑通，架构上预留自建消息通道的替换点。
- 所有业务数据（用户、好友、群资料、推送 token）自有，IM 只作为消息管道。

## 2. 架构原则

1. **UI 不直接依赖任何 IM SDK**：所有消息能力收敛到 `ChatEngine` 接口。
2. **本地优先**：消息先落 Room，再等网络回调，弱网也能读。
3. **服务端只做补集**：登录鉴权、UserSig、好友/群资料、审核回调、推送注册。
4. **密钥不进客户端**：`UserSig` 与任何 Secret 只在服务端签发。
5. **可迁移**：消息模型、会话模型、状态机由自己定义，换通道不换 UI。

## 3. 技术选型

| 层 | 选型 | 备注 |
| --- | --- | --- |
| 客户端 | Kotlin 2.0 + Jetpack Compose (Material 3) | 单端原生，Compose 迭代效率最高 |
| 架构 | MVVM + 单向数据流 | ViewModel 持有 `StateFlow`，UI 只消费状态 |
| DI | Hilt | 标准 Android 依赖注入 |
| 本地存储 | Room + DataStore | 会话/消息走 Room，登录态与主题走 DataStore |
| 异步 | Coroutines + Flow | 消息流全链路响应式 |
| 消息通道（规划） | 腾讯云 IM 核心 SDK | M0 先用本地引擎模拟完整交互 |
| 音视频（规划） | 腾讯云 TRTC | 与 IM 同账号体系，信令走自定义消息 |
| 服务端 | Node.js 标准库（M0） | 零依赖即可运行、可测试；M1 可平滑迁 NestJS |
| 数据（服务端） | 内存存储（M0）→ PostgreSQL | M0 只验证协议与鉴权 |
| 对象存储（规划） | COS 直传 | 客户端拿临时密钥，不经过业务服务器 |
| 推送（规划） | 厂商通道 + FCM | 国内离线消息与来电唤醒的关键 |

## 4. 里程碑

### M0 · 可运行骨架（本轮交付）

**目标**：在没有任何云账号的前提下，App 可安装、可登录、可聊天；服务端协议可独立运行与测试。

范围：

- Android 工程、主题、导航、Hilt、Room 全部就位。
- 登录页（本地演示，验证码 `123456`）。
- 会话列表：置顶、未读、搜索、新建会话、删除会话。
- 聊天页：文本消息、日期分割、发送状态、模拟对方回复、输入中状态、长按复制。
- 设置页：账号信息、浅色/深色/跟随系统、退出登录。
- 本地演示引擎：首次启动自动播种 4 个会话，回复内容按人设生成。
- BFF：短信验证码（mock）、JWT 登录、UserSig 生成、推送 token 注册。
- 单元测试：时间格式化、JWT、UserSig、验证码状态机、HTTP 接口。
- CI：Android 构建 + 单测、服务端测试。

验收标准：

- `./gradlew :app:assembleDebug :app:testDebugUnitTest` 通过。
- `cd server && npm test` 全部通过。
- App 冷启动进入登录页，登录后进入会话列表，收发消息刷新后仍在。
- 仓库无任何密钥、`local.properties`、构建产物。

非目标：真实云 IM 联调、音视频、富媒体、真实短信、多端同步。

### M1 · 接入真实消息通道

- 接入腾讯云 IM：`TencentChatEngine` 实现 `ChatEngine`。
- 服务端签发 UserSig，客户端完成 IM 登录。
- 文本消息、会话漫游、已读回执对接到现有 UI。
- BFF 接入 PostgreSQL 与真实短信服务。
- 验收：两台设备互发消息，弱网可重发，重启后消息不丢。

### M2 · 富媒体与群聊

- 图片、语音、视频、文件消息；COS 直传与进度。
- 群创建、邀请、成员管理、群公告、免打扰。
- 消息失败重试、草稿、@ 提醒。
- 验收：大文件有进度与取消；群成员变更实时生效。

### M3 · 音视频通话

- TRTC 1v1 与小组通话，IM 自定义信令。
- 来电全屏页、离线厂商透传唤醒、通话记录。
- 验收：锁屏状态下可收到来电并接通；弱网自动降级。

### M4 · 上架与稳定性

- APP 备案、隐私政策、权限最小化、内容审核。
- 崩溃监控、性能基线、包体积治理、灰度发布。
- 验收：通过目标应用商店审核；崩溃率与启动时长达标。

## 5. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 国内厂商离线唤醒限制 | 来电收不到 | M3 单独验证，逐厂商接通道，做真机矩阵 |
| IM SDK 与 UI 强耦合 | 后期迁移成本高 | 已有 `ChatEngine` 边界，禁止 UI 引用 SDK 类型 |
| 消息重复/乱序 | 数据错乱 | 依赖 IM 的 `seq` 与去重；本地用 `clientMsgId` 幂等 |
| 合规 | 无法上架 | M4 前完成备案、隐私协议、审核接入 |
| 个人开发精力 | 范围失控 | 每期只做验收清单内的事，非目标明确写出 |

## 6. 工程规范

- 分支：`main` 保持可构建；功能分支 `feat/xxx`。
- 提交：祈使句 + 说明“为什么”，一次提交只做一件事。
- 质量门禁：本地构建通过、单测通过、无明文密钥。
- 文件边界：`local.properties`、`.env`、`*.jks`、`build/`、`node_modules/` 永不入库。
- 文档：架构变更同步更新 `docs/ARCHITECTURE.md`，接口变更同步 `docs/API.md`。
